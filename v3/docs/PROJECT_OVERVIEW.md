# 一个研发问题如何被接续

使用者提出问题、补充限制并查看进度，系统需要判断后续输入是否属于同一项工作，已发生的执行有什么证据，以及何时可以反馈。Super-Agent 的设计以持续问题为中心；下述流程是职责分工，具体能力仍须对照[当前状态](CURRENT_STATUS.md)的版本与验收范围。

## 从消息到工作目标

来源负责识别平台安装、事件和发送者，并按来源、身份和策略检查是否接收。一个 **Thread** 是可关联问题的持续上下文；**Ticket/Task** 表示工作目标及其生命周期；**Run** 是针对某个输入与版本的一次执行尝试。因此，后续消息可能补充已有任务，而不必每条都创建新任务；一项任务也可能经过多个执行尝试。[架构设计原件](super-agent-v1/ARCHITECTURE.md)

重复投递、迟到输入、来源权限变化以及同一话题内的不同问题会使关联变难。设计中的有效订阅可把后续输入投递给原任务；需判断归属时，Router 提出受限候选，Engine 再核对身份、策略、版本和预算。订阅不会将普通上下文自动变成执行授权。[Router 与订阅设计](super-agent-v1/ARCHITECTURE.md#5-fast-pathrouter-与订阅)

## 分配、执行与验证

Scheduler 根据任务、租约和资源安排 Assignment；Worker 在获准范围和隔离工作区执行，Harness 支持单次 Run 的工具循环。使用者撤权、目标修订或执行代次变化时，需要重新检查哪些操作仍被允许。执行结果应携带产物及回执；正式 Verifier、业务判断、具体审批和外部送达分别记录。旧架构原件标记 PLANNED，不代表其中所有接口均已通过真实平台验收。[架构原件](super-agent-v1/ARCHITECTURE.md) · [验收协议](super-agent-v1/ACCEPTANCE.md)

## 为什么订阅值得单独考虑

若已有任务的后续消息每次都重新询问 Router，系统可能重复花费模型调用。E/F 受控实验中，F 通过订阅直达与批处理减少了 Router 调用；这说明固定负载下可以减少路由次数，但不能据此认定模型协调推理普遍改善。[实验解读](EVALUATION_SUMMARY.md)
